# S9.4 — Remove production duplication in the auth pages and the Create\* dialogs

**Jira:** SPRIN-49, under SPRIN-44 (E9 Code quality standard)
**Date:** 2026-07-27
**Branch:** `refactor/dedupe-form-scaffolding`

Pass B's last concern. `npm run lint:standards` has been at 0 since `4334ace`, so the
complexity work is finished; production-to-production duplication is the only thing
between here and step 4 of the audit's sequencing — folding the rules into `lint` and
letting `verify` gate them.

## What is actually duplicated

Re-measured at `cf182d9` with `jscpd src e2e --min-lines 5`, filtered to clones where
**neither** side is a test file, and with generated code set aside:

| Lines | Sites | What |
|---|---|---|
| 33 + 14 | `LoginPage.tsx` ↔ `SignupPage.tsx` | form wrapper, email field, password field, root-error paragraph, submit button |
| 21 | `CreateSprintDialog.tsx` ↔ `CreateTicketDialog.tsx` | the import block |
| 15 + 11 | `CreateProjectDialog.tsx` ↔ `CreateTicketDialog`/`CreateSprintDialog` | root-error, `DialogFooter`, submit button |
| 14 | `CreateProjectDialog.tsx` ↔ `CreateSprintDialog.tsx` | dialog header and form open |

Two clones are **excluded deliberately**, not fixed: 28 lines inside
`lib/database.types.ts` (generated by the Supabase CLI — editing it would be undone by
the next regeneration) and 7 lines of `index.css` (Tailwind theme blocks, where the
repetition is the format). Any future duplication gate must exclude both.

One clone jscpd missed because it is under the line threshold: **`selectClass` is
defined identically in `CreateTicketDialog.tsx:52` and `EditableText.tsx:8`** — the same
78-character Tailwind string, twice.

The signal underneath the numbers: five components each hand-roll the same three
form conventions — *how a form-level error is shown*, *how a submit button reflects
`isSubmitting`*, and *how a create dialog opens, resets and closes*. That is what gets a
name here, not the lines.

## Scope decision: the auth pages are in, markup only

David's call, 2026-07-27. `LoginPage`/`SignupPage` hold the single largest clone, so
leaving them out would close E9 with the biggest one unfixed. But they are also an
authentication surface, so the extraction is bounded:

- **Every `supabase.auth.*` call stays in its own page.** No shared submit hook.
- **Every error-mapping decision stays in its own page** — `isDuplicateSignup`, the
  `DUPLICATE_MESSAGE`/`GENERIC_ERROR` constants, and the CLAUDE.md rule that a raw GoTrue
  string is never surfaced. The shared component decides only *where* an error is
  painted, never *what it says*.
- **`autoComplete` on the password field stays per-page and explicit.** It is the one
  attribute that genuinely differs (`current-password` on login, `new-password` on
  signup) and the one a careless shared default would silently collapse. It is therefore
  a **required prop typed as the two-member union** `'current-password' | 'new-password'`
  — no default value, so omitting it is a compile error and a typo is a compile error.

Per CLAUDE.md this diff touches authentication, so it gets the deep multi-agent review
in addition to the standard peer and security passes.

## The four units

Each is small, has one job, and is used by at least two callers. Nothing here is built
for a caller that does not yet exist.

### 1. `src/routes/form-primitives.tsx` — the react-hook-form primitives

```tsx
export const selectClass = '…'                                  // moved, not new
export function FormRootError(): ReactElement | null
export function SubmitButton(props: {
  label: string
  pendingLabel: string
  className?: string
}): ReactElement
```

`FormRootError` takes no props. It reads the form-level error itself and renders the
`role="alert"` paragraph, or nothing. `SubmitButton` reads `isSubmitting` itself and
handles both the `disabled` attribute and the label swap.

**Both subscribe via `useFormState()`, not `useFormContext().formState`.** This is the
one genuinely load-bearing implementation detail in the whole story. `useFormContext()`
hands back the *parent's* formState proxy; reading `errors` off it from a child works
only by a side effect on the parent's subscription flags. `useFormState()` establishes
the child's own subscription, which is what it exists for — and it is what this repo's
own `useFormField` in `src/components/ui/form.tsx:42` already does. Getting this wrong
produces a form-level error that is set but never painted, which is precisely the
failure `LoginPage.test.tsx`'s `findByRole('alert')` catches.

`selectClass` moves here from `EditableText.tsx`. It is a form-control style used by
both families of code — the RHF forms and the inline-edit sidebar — so its current home
inside a single-component file is the wrong one either way.

### 2. `src/routes/CreateDialog.tsx` — the create-dialog shell

```tsx
export function CreateDialog<T extends FieldValues>(props: {
  trigger: string
  title: string
  description: ReactNode
  submitLabel: string
  form: UseFormReturn<T>
  onSubmit: (values: T, close: () => void) => void | Promise<void>
  onClosed?: () => void
  children: ReactNode
}): ReactElement
```

Owns the `open` state, the trigger button, the dialog chrome, the `<Form>`/`<form>`
wrapper, the `FormRootError`, the `DialogFooter` and the `SubmitButton`. The caller
supplies only its fields, as `children`.

Two shapes were considered for closing on success. Letting the shell close itself when
`onSubmit` resolves without a root error is fewer characters and wrong — it makes
"did it close?" depend on an invisible reading of form state, and it silently changes
behaviour for any future handler that succeeds *and* warns. **`onSubmit` receives an
explicit `close` callback** instead: the call site still says, in as many words, that a
successful create closes the dialog.

`onClosed` exists for exactly one caller — `CreateProjectDialog`, which must clear its
`keyEdited` flag alongside the form reset — and is optional because the other two have
nothing extra to do.

`pendingLabel` is **not** a prop. All three dialogs say `Creating…`, and the component
is named `CreateDialog`; a prop would be an option with one value.

`form.reset({ name: '', key: '' })` in `CreateProjectDialog` becomes a bare
`form.reset()` inside the shell. These are equivalent — react-hook-form's `reset()`
with no argument resets to `defaultValues`, and that form's `defaultValues` are exactly
`{ name: '', key: '' }`.

### 3. `src/routes/AuthCredentialFields.tsx` — the shared login/signup fields

```tsx
export function AuthCredentialFields(props: {
  passwordAutoComplete: 'current-password' | 'new-password'
}): ReactElement
```

The email field and the password field, nothing else. Signup's optional display-name
field stays in `SignupPage` — it belongs to one page, so it is not shared.

The `<Form>`/`<form>` wrapper is **left inline in both pages** rather than absorbed into
an `AuthForm` shell. It is two lines, it is where `handleSubmit(onSubmit)` is wired, and
on an auth page the line that says which handler runs on submit should be visible in the
page that owns the handler.

### 4. Callers

`LoginPage`, `SignupPage`, `CreateProjectDialog`, `CreateSprintDialog` and
`CreateTicketDialog` are rewritten against the above. `TicketReferenceSelect` and
`TicketDetailSidebar` change only the module they import `selectClass` from.
`EditableText.tsx` loses the `selectClass` export and keeps `EditableText` and
`FieldLabel`.

## Not in scope

- **Renaming `EditableText.tsx`.** Memory records it as a form-primitives module living
  under a single-component name. After this story that is less true, not more: what
  remains beside `EditableText` is `FieldLabel`, and both belong to the same inline-edit
  family. The naming debt stays recorded and unpaid; paying it would touch six import
  sites for no behavioural gain.
- **The test-to-test clones.** 67 of the 78 baseline clones involve a test file, where a
  repeated arrange-block is deliberate and readable. ADR 0002 already exempts tests from
  the size rules for the same reason.
- **Folding the rules into `lint`/`verify`.** That is the audit's step 4 and the next
  story, not this one. One concern per PR.

## Testing

The five existing test files for the touched components — `LoginPage.test.tsx`,
`SignupPage.test.tsx`, and the three `Create*Dialog.test.tsx` — are **not modified**.
They are behaviour-level throughout (`getByLabelText`, `getByRole`, `findByText`), so
they will exercise the rewritten internals unchanged. That is what makes the
behaviour-preservation claim checkable rather than asserted, and it is the same
constraint S9.1 and S9.2 ran under.

Three new test files cover the new seams, and they exist because the old code's tests
do not reach them:

- `form-primitives.test.tsx` — the root error appears when set and is absent when not;
  the submit button is disabled and shows `pendingLabel` while submitting.
- `CreateDialog.test.tsx` — opening; **the form resets when the dialog closes**;
  `onClosed` fires on close; `onSubmit` receives a `close` that actually closes. None of
  the reset-on-close behaviour is covered today by any of the three dialogs' own tests,
  so moving it without a new test would move it into a blind spot.
- `AuthCredentialFields.test.tsx` — **the password input carries exactly the
  `autoComplete` it was given, asserted for both union members**, and the email input
  keeps `type="email"` and `autoComplete="email"`. No test asserts this today; the
  attribute is currently protected by nothing but the fact that it is written twice.

Every new test must be shown to fail against a deliberately broken implementation before
it is believed. A test that passes on first write proves nothing yet.

## Acceptance criteria

1. `jscpd src e2e --min-lines 5` reports **no clone where both sides are production
   files**, other than the two excluded above (`lib/database.types.ts`, `index.css`).
   Re-measured, not asserted.
2. `selectClass` is defined once in the repository.
3. The five existing test files listed above are byte-unchanged, and pass.
4. Auth behaviour is untouched: no `supabase.auth.*` call and no user-facing error string
   moves out of `LoginPage`/`SignupPage`, and the password `autoComplete` remains
   `current-password` on login and `new-password` on signup.
5. `npm run verify` is green and `npm run lint:standards` still reports 0.
6. The live signup and login integration suites still pass — the gap between
   `npm test` and `npm run test:unit` is still seven files.
