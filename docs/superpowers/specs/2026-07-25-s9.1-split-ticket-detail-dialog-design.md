# S9.1 — Split `TicketDetailDialog` into cohesive units (Pass B)

**Tracker:** SPRIN-45, under SPRIN-44 (E9 Code quality standard)
**Date:** 2026-07-25
**Kind:** Behaviour-preserving refactor. Zero user-visible change.

---

## Why this file, and why now

The standards baseline (`docs/standards-audit-2026-07-25.md`) found seven violations.
Three of them are this one file:

```
src/routes/TicketDetailDialog.tsx:223  complexity 45          (limit 10)
src/routes/TicketDetailDialog.tsx:223  cognitive complexity 44 (limit 15)
src/routes/TicketDetailDialog.tsx:567  file 945 lines          (limit 400)
```

It is the only file where the standard told us something we did not already know.
The baseline also recorded *why it is not a tidy-up-at-the-end job*: it sits on the
ticket write path and carries the documented optimistic-write race, so it gets its
own slice and a deep review rather than being swept up in a big-bang pass.

`max-lines` counts with `skipBlankLines` and `skipComments`, so the target is the
**file under 400 countable lines** (it is 1165 raw / 945 countable — the file is
comment-dense, and those comments are load-bearing history that must survive the
move, travelling with the code they explain).

ADR 0001 turns `max-lines-per-function` off for `.tsx`, so T1 does not apply. The
three numbers above are the whole job.

## The governing constraint: the test file does not change

`TicketDetailDialog.test.tsx` holds **64 tests** and already covers every behaviour
the acceptance criteria name, plus the specific behaviours listed in the table
below — each one confirmed by the peer review, which broke the code and watched
the relevant test fail:

| Behaviour at risk | Existing test |
|---|---|
| Escape cancels the field, not the dialog | `'Should not save{Escape}'` (line ~293) |
| Escape clears the add-deliverable draft, dialog stays open | `clears the add-deliverable draft on Escape without closing the dialog` |
| Focus returns to the field trigger after commit/cancel | `returns focus to the field trigger button after commit (Enter) and after cancel (Escape)` |
| Successful deliverables write invalidates the AI trace | `invalidates a stale decomposition when a deliverable is edited while the panel is open` |
| Failed deliverables write does **not** invalidate | `keeps the decomposition when a deliverable write fails` |
| Deliverable writes are serialized | `serializes deliverable writes: Add is disabled while a save is in flight` |
| Field-scoped rollback, not whole-ticket | `stale render-time-snapshot rollback would revert the WHOLE ticket …` (line ~269) |
| Dead-instance save must not clobber a reopened instance (Ultracode Critical) | `does not let a stale in-flight save from a closed instance clobber a reopened instance edit` |
| Optimistic merge against the latest ticket, not a render snapshot | line ~206 |

**Limit, recorded honestly:** the table above is not exhaustive of everything a
refactor could break. The peer review ran 34 mutation tests against the split and
found 11 single-prop mutations across the new component boundaries — props
re-threaded by hand from one file into another — that survive the full 426-test
run: for example dropping `onEditingChange` from the Context or Labels field,
dropping `disabled={deliverables.pending}` from a remove button, dropping the
parent-epic self-filter, dropping `Math.max(0, …)` from the coverage count, or
making either action dialog dismissable mid-flight. None is a regression, and all
11 were equally unpinned before this refactor — the existing 64 tests never
asserted them either. Closing them is follow-up work, not part of this slice.

So the design constraint that does the most work is this:

> **`src/routes/TicketDetailDialog.test.tsx` is not edited. Not one line.**
> All 64 tests keep passing against the refactored tree.

That converts "behaviour is preserved" from an assertion into a proof, for
everything those tests cover. New tests are **added** in new files; they never
replace an existing one. If a change to the existing test file ever looks
necessary, that is the signal that the refactor has changed behaviour — stop and
reconsider, do not edit the test.

`ProjectShell.test.tsx` mounts this dialog **unstubbed** ("no stubs on either
side", line ~445). That is the seam that broke in S7.1, when a type-level check
passed and three sibling tests went red. It also stays unedited.

## Architecture: logic to `src/lib`, markup to `src/routes`

The codebase already draws this line, and `src/lib/auth-context.ts` sets the
precedent: `useAuth` lives apart from `AuthProvider`, in its own `.ts` module,
rather than being exported alongside the provider component. The other reason
pulls the same way: per ADR 0001, `max-lines-per-function` is off for `.tsx` but
on everywhere else, so moving substantial logic out of the component and into a
`.ts` hook module puts it back under T1's 30-line cap — the cap the component
itself is exempt from precisely because it is markup-heavy, not logic-heavy.
Hooks therefore belong in `src/lib`, alongside the pure helpers
(`parseBlockReason`, `parseLabels`, `parseDeliverables`) they sit next to.

`eslint-plugin-react-hooks@7` is the compiler-backed rule set: **writing
`ref.current` during render and setting state in an effect are hard errors.** The
existing code is shaped around both rules (the `ticketRef` sync effect exists
precisely because of the refs rule). Every extracted hook inherits those
constraints.

### New logic modules (`src/lib`)

| Module | Exports | Owns |
|---|---|---|
| `ticket-commit.ts` | `pickFields`, `useIsMounted`, `useTicketCommit` | The optimistic write engine: `ticketRef`, mount guard, ticket-scoped error, field-scoped revert/reconcile, `applyServerRow` for the non-optimistic block path |
| `ticket-deliverables.ts` | `useDeliverables` | The epic deliverables list: serialization flag, add/remove/edit, draft |
| `ticket-decomposition.ts` | `useDecomposition` | The AI trace: proposals, selection, coverage gaps, scope creep, estimate total, in-flight flags, `runDecompose`, `acceptSelected`, `reset` |
| `ticket-actions.ts` | `useBlockFlow`, `useDeleteFlow` | The two kebab actions and their dialog state |
| `tickets.ts` *(edit)* | `+ parseStoryPoints`, `+ parseSummary` | Joins `parseBlockReason` / `BLOCK_REASON_MAX`, its existing neighbours in the same concern |

`useTicketCommit(ticket, onUpdated)` returns
`{ commit, error, setError, clearError, applyServerRow, isMounted }`.

`parseStoryPoints` and `parseSummary` move to `tickets.ts` rather than a new
module because that file already owns exactly this concern — hand re-validation of
the same shapes `CreateTicketDialog`'s zod schema enforces — and at 184 raw lines
it has ample headroom under the 400 limit.

### New presentation modules (`src/routes`)

| File | Exports |
|---|---|
| `EditableText.tsx` | `EditableText`, `FieldLabel`, `selectClass` |
| `TicketDetailHeader.tsx` | `TicketDetailHeader`, `TicketBlockedBanner` |
| `TicketMainFields.tsx` | `TicketMainFields` (summary, description, acceptance criteria) |
| `TicketEpicSection.tsx` | `TicketEpicSection`, `TicketDeliverablesEditor` |
| `TicketDecompositionPanel.tsx` | `TicketDecompositionPanel` |
| `TicketDetailSidebar.tsx` | `TicketDetailSidebar` |
| `TicketActionDialogs.tsx` | `TicketBlockDialog`, `TicketDeleteDialog` |

Flat and PascalCase, matching the other 30-odd files in `src/routes`. No
subdirectory: the repo is flat, and a `TicketDetail*` / `Ticket*` prefix keeps the
set greppable without breaking the convention.

Files pair two components only where they are one concern — status display
(header + banner), the epic-only block (section + its deliverables editor), the two
kebab dialogs. `allowConstantExport: true` in the ESLint config is what lets
`selectClass` sit beside `EditableText`.

`TicketDecompositionPanel` stays on its own: it is the largest and most distinct
piece, and pairing it would rebuild a grab-bag.

### What stays in `TicketDetailDialog.tsx`

The dialog keeps exactly what only it can hold: the prop contract, the hook calls,
the two dialog-open booleans (the kebab in the header opens them, so they cannot
live in either child), the Escape policy, and the composition of the seven
children. It becomes a readable assembly rather than an implementation.

## The two load-bearing couplings

These are the parts a refactor breaks silently while looking like tidying up.

### A. The Escape contract

`onEscapeKeyDown` needs two facts that live below it: is a field mid-edit, and is
focus in the add-deliverable input with a non-empty draft. Radix dismisses at the
document level in the capture phase, so a local `stopPropagation` in a child
cannot keep the dialog open — the decision **must** be made in the parent.

Order matters and is observable: mid-edit is checked **first** and returns early,
so Escape while a field is mid-edit does *not* also clear the deliverable draft.

**Two mechanisms were considered.**

An *escape-consumer registry* — children register `() => boolean` handlers, the
parent consumes if any returns true — is the more "designed" option and was
rejected. Handler order would follow mount order rather than being stated in one
place, and a registry that ran every handler would clear the draft on a mid-edit
Escape, which is a behaviour change. A reviewer would be right to distrust it.

**Chosen: lift the draft.** The parent keeps `editingCount`, `deliverableDraft`
and `newDeliverableRef`; `TicketDeliverablesEditor` becomes a controlled component
receiving draft, setter and ref as props. `onEscapeKeyDown` is then carried over
with its logic and its comments intact — no new mechanism to verify, and the
ordering stays written down where it is read. `useDeliverables` owns the draft
state so the parent's own body stays thin.

`onEditingChange` is threaded as a prop to the three components that render an
`EditableText` (main fields, epic section, sidebar). A context would be tidier to
look at, but it would change *how* the count is maintained — from an explicit
callback to `EditableText` mount/unmount — and that is exactly the kind of
invisible substitution this slice must not make.

### B. Deliverables write invalidates the AI trace

A **successful** deliverables write resets proposals, selection, coverage gaps,
scope creep and estimate total, because the write shifts the `covers` indices they
were computed against — a "delivers" chip would otherwise name the wrong
deliverable and the coverage count could go negative. A **failed** write must not,
because rollback keeps the indices valid. The scope is deliberate and documented
in PR #40: editing context or summary does **not** invalidate.

Today five setters are called in a row, and that same five-line block is
**repeated in three places** — `writeDeliverables`, `acceptSelected`, and the
Discard button. Forgetting one is a live hazard, and it is precisely the failure
the invalidation exists to prevent.

**Chosen: `useDecomposition` exposes `reset()`.** The five fields are cleared in
one function defined once and used by all three call sites. The parent wires the
deliverables hook's success callback to it.

A `key={traceEpoch}` remount was considered and **rejected on evidence**. It is
atomic too, and the pattern is already load-bearing here (`ProjectShell` renders
this dialog with `key={selected?.id ?? 'none'}`). But it resets *everything* the
panel holds, and the current reset deliberately spares two things: `aiError`
(which survives a deliverables write today) and an in-flight `decomposing` call
(whose result the current code would still apply). Remounting would change both.
`reset()` gets the same atomicity gain with no behaviour delta and nothing to
disclose — which is the whole point of this slice.

Note this leaves an existing quirk in place: a decompose in flight when a
deliverables write lands will still deliver its now-stale proposals. That is
pre-existing, untested, out of scope here, and recorded below.

## Testing

**Unchanged:** `TicketDetailDialog.test.tsx` (64 tests) and `ProjectShell.test.tsx`.
These are the proof of behaviour preservation and the reason this refactor is
safe to attempt at all.

**Added** — one test file per new lib module. The two Ultracode Critical guards get
**direct** unit tests for the first time, instead of only being exercised through
the dialog:

- `ticket-commit.test.ts` — field-scoped revert on failure; field-scoped reconcile
  plus refreshed `updated_at` on success; the unmounted-instance bail; the
  wrong-identity fallback when `ticketRef` has moved to a different ticket or
  `null`; ticket-scoped error clearing.
- `ticket-deliverables.test.ts` — serialization rejects a second concurrent write;
  draft cleared only on a successful add; edit-to-blank removes; `onWritten` fires
  on success only.
- `ticket-decomposition.test.ts` — `reset()` clears all five fields and spares
  `aiError`; partial accept-failure still clears the panel; unauthenticated vs
  unreachable error copy.
- `ticket-actions.test.ts` — block requires a valid reason; duplicate unblock is
  guarded; both apply the server row field-scoped.

The rule for each new test: watch it fail before trusting it. "Would a test catch
this?" is settled by breaking the code, not by arguing about it.

## Acceptance criteria

1. `TicketDetailDialog.tsx` is under 400 countable lines; its component function
   meets complexity ≤ 10 and cognitive complexity ≤ 15.
2. The optimistic write engine lives in one named unit with direct tests,
   including the unmounted-instance guard and the wrong-identity fallback.
3. The Escape contract is preserved in all three branches, proven by the
   unchanged existing tests.
4. A successful deliverables write still invalidates the trace; a failed one still
   does not. Proven by the unchanged existing tests.
5. All 64 existing dialog tests and the `ProjectShell` tests pass **with the test
   files unedited**.
6. `npm run lint:standards` reports zero findings for this file, and the repo-wide
   count does not grow.
7. `npm run verify` is green with the live integration suites running, not skipped.
8. Every load-bearing comment survives the move, attached to the code it explains.

## Out of scope

- The same-field out-of-order optimistic-write race (Ultracode-E). This slice moves
  it into a directly testable unit; it does not change it. The `// NOTE:` travels
  with `commit`.
- The stale in-flight decompose described in section B.
- `ProjectShell.tsx` complexity 25, `src/lib/ai.ts`, and the `e2e` spec complexity
  — three of the other baseline findings. One concern per PR.
- The prod-to-prod duplication findings (auth form, `Create*Dialog` scaffolds).
- Folding the standards rules into `lint` / `verify`. That waits until production
  code is clean.
