# ADR 0005 — The duplication gate

**Status:** Accepted, 2026-07-28
**Enforces:** T6, duplication under 3 percent, from
`/var/www/CodingStandards/core/THRESHOLDS.md`

## Context

The standard's sixth threshold, T6, caps duplication at 3 percent, gated by
jscpd across all three of the standard's stacks. E9's Pass B (S9.1–S9.4) took
production clones from 11 down to 3, and all three survivors sit inside the two
files any gate must exclude anyway: `src/lib/database.types.ts` (generated by
the Supabase CLI, not hand-maintained) and `src/index.css` (Tailwind `@theme`
blocks, whose whole job is declarative repetition). A duplication gate is only
worth adding once the count outside those exclusions is already zero — gating
it earlier would have meant gating on debt nobody had chosen to accept yet.

jscpd 5.x ships as a native platform binary with no JavaScript API, so the only
way to drive it is the CLI (`jscpd/run-jscpd.js`, its Node shim). That shape —
one subprocess call, its exit code and its JSON report — is what
`scripts/check-duplication.mjs` wraps, for the same reason a bare `jscpd
--threshold 3` in `package.json` is not enough: a misconfigured scan can report
a flawless 0.00% while having measured nothing, and a gate that cannot tell
"clean" from "did not look" is worse than no gate.

## Decision

Scan `src` only (`PRODUCTION_SCOPE`), the same production/test split ADR 0002
already draws for the size thresholds.

`IGNORE_PATTERNS`, each justified once, not inherited:

- `**/*.test.ts`, `**/*.test.tsx`, `**/*.spec.ts`, `src/test/**` — ADR 0002's
  reasoning extended to T6: a naive scan with no ignore list measures 5.30%
  (870 of 16,429 lines), almost all of it arrange blocks in the integration
  suites, and gating that would mean restructuring suites to satisfy a metric.
- `src/lib/database.types.ts` — generated from the live schema, not
  hand-maintained.
- `src/index.css` — Tailwind `@theme` blocks; declarative repetition is the
  file's job.

`src/components/ui/**` is deliberately **not** in that list, even though both
of `eslint.config.js`'s size-threshold overrides exempt vendored shadcn.
Measured directly: including it adds 9 files / 643 lines to the scan (55 → 64
files, 5,179 → 5,822 lines) and still yields 0 clones either way. An exclusion
that buys nothing today is one nobody revisits when it starts hiding something.
If a future `shadcn add` ever trips this gate, adding the exclusion is one line
in `IGNORE_PATTERNS` plus an ADR addendum — not a reason to add it pre-emptively.

`SENSITIVITY` is stated, not inherited: `minLines: 5`, `minTokens: 50`, `mode:
'mild'`, `maxSize: 1048576` (bytes). All four of jscpd's detection modes
produced identical results on this tree, so pinning `mode` buys future
determinism rather than changing today's verdict — the same lesson as the
ruff-version drift that once reddened `api/`'s CI on unchanged code: a gate
whose verdict can move without a commit is not a gate.

`LIMITS.maxPercentage` is 3, matching T6, and a scan at exactly 3% passes —
that matches jscpd's own `--threshold` semantics, so a hand-run CLI and this
script never disagree. `LIMITS.minSources` (40 files) and
`LIMITS.minScannedLines` (3,000 lines) are **tripwires, not size targets**: at
pin time the real scan measured 64 files / 5,822 lines, comfortably clear.
They exist only to catch a broken ignore glob or scope — an empty or
near-empty scan reporting a perfect 0.00% — and they say nothing about how
much code this repo should have. They can only ever become more lenient than
the day they were set; raising them to "track growth" would be a category
error.

A percentage alone cannot be trusted, because jscpd can silently measure far
less than the whole tree while still reporting a clean number. The script
refuses to run — rather than reporting a result — in each of these cases,
every one demonstrated against the pinned binary rather than assumed:

- **An external jscpd config file is discoverable.** jscpd auto-discovers
  configuration from the scanning process's cwd (`.jscpd.json`, `.jscpdrc`,
  `.jscpdrc.json`, `.jscpd.js`, or a `"jscpd"` key in `package.json`) and lets
  it silently override every option this script does not pass as an explicit
  CLI flag. A 24-byte `.jscpd.json` (`{"maxSize": "6kb"}`) was enough to
  exclude the twelve largest production files — the whole data layer and
  routes — from the scan while a planted, real duplicate went unreported and
  the summary still read as a healthy 0%.
- **A `.ignore` file exists in the scan scope or any ancestor directory, up to
  the filesystem root.** jscpd honours this file family regardless of
  `--no-gitignore`, which switches off only the `.gitignore` family (a root or
  nested `.gitignore`, `.git/info/exclude`, and even a machine-global git
  excludes file) — not `.ignore`, for which jscpd 5.0.14 has no `--no-ignore`
  flag. Refusing is the only honest response. One `.gitignore` line hiding a
  tracked, shipping 212-line duplicate turned a real 3.4968% / exit 1 into
  `64 files / 5822 lines, 0 clones, 0%` / exit 0 — a summary byte-identical to
  the honest run.
- **The optional scope argument fails validation.** It may not start with `-`
  (otherwise a raw jscpd flag — `--config=`, `--max-size=6kb`, `--ignore=...`
  — could travel in as an argv token and redefine what the gate measures while
  it still reports a clean 0% and exits 0) and must resolve to an existing
  directory.
- **A file in scope is over the 1,048,576-byte cap.** jscpd silently drops an
  over-cap file from the scan, and the file/line floors are structurally blind
  to the omission — the denominator never moves, so the summary is
  byte-identical to an honest run. Two verbatim 2.4 MB duplicates dropped into
  `src/lib` produced the same `64 files / 5822 lines, 0 clones, 0%` as the
  clean baseline. This check deliberately does **not** consult
  `IGNORE_PATTERNS`: an oversized file blocks the gate even if it would never
  have been measured anyway, because "excluded" and "too big to measure" are
  not the same fact and should not look the same from inside the guard. The
  alternative — a hand-rolled glob matcher against the ignore list, or a new
  dependency, just to tell those two cases apart — was rejected as more
  machinery than the case has earned; nothing in this repo is near the cap
  today (the largest file under `src` is 64,807 bytes, 16.2× under it).
- **A symlink exists inside the scan scope.** jscpd does not follow links, so
  it and anything beneath it would be dropped from the scan without a word
  while still shipping. A scan *root* that is itself a symlink is fine and
  deliberately not refused — jscpd traverses that normally — only links found
  *inside* the tree are rejected, since following them the other way (a link
  pointing out of `src`) would pull foreign code into the denominator and
  could dilute a real violation under the 3% bar.

`.mjs` files are outside `eslint.config.js`'s threshold block, which targets
`**/*.{ts,tsx}` only — `scripts/check-duplication.mjs` is therefore not linted
by the standard's T1–T5 rules at all, and was held to them by hand rather than
mechanically. That is a deliberate limitation, not an oversight: widening the
block to reach `.mjs` would also newly flag `scripts/check-bundle.mjs`'s
31-line `main`, forcing a metric-driven split of an untested security control
— exactly the trade ADR 0001 already rejects for `.tsx` markup, applied here to
a different file type.

## Consequences

- Test-file duplication is real — a naive scan with no ignore list measures
  5.30% (870 of 16,429 lines) — and stays unmeasured and accepted, on the same
  reasoning ADR 0002 already gave for T1/T5 in test files (see its addendum).
- The 40-file / 3,000-line floor will read as increasingly lax as the repo
  grows. That is fine: it exists to catch a broken glob, not to track size, and
  it can only ever loosen relative to the day it was pinned, never tighten on
  its own.
- A native jscpd binary, with no JavaScript API, now sits inside the required
  `verify` gate. If it becomes unavailable — a missing binary, a broken
  install — `assertScanSucceeded` makes the script fail closed rather than
  silently pass.
- `scripts/check-duplication.mjs` is not linted by the standard's own
  thresholds (see the `.mjs` limitation above); its compliance with them is
  asserted by comment and reviewed by hand, not enforced by tooling.
- Every refusal behaviour above is pinned by `scripts/check-duplication.test.mjs`,
  including process-level subprocess tests that plant a real external config
  file, a real `.gitignore` and `.ignore`, a real oversized file and a real
  symlink, and assert the gate refuses each one — not merely that a pure
  function returns the right string.
